# RAG与工具如何落实租户和用户权限

## 直接回答

先验证身份，再从可信身份确定租户和用户权限。RAG 在检索入口限制可见文档，片段返回和引用展示时复核权限；工具不仅检查“能否调用”，还要检查“能对哪个租户的哪个对象做什么”。默认拒绝未知身份、未知租户和缺少授权依据的对象。

生产设计建议：将权限上下文作为服务器内部数据传递，不能由提示词、模型参数或客户端自报 tenantId 决定。日志、缓存、会话记忆、执行历史和审批列表也属于授权面，不能只保护主问答接口。

## 实际场景

员工有订单查询工具权限，但只允许查询自己部门的订单。模型给出一个订单编号，并不证明该订单属于当前用户；工具执行器需要按租户、部门或对象访问规则再次限制查询。

ai-platform 的 GatewayAuthFilter 只检查 token 是否以 sk- 开头，这是教学鉴权，不验证签名、有效期和身份归属。网关又从请求读取 tenantId，因此不能将现状称为可信多租户认证。正式系统必须替换此边界，而不是在前缀检查上补几条字符串规则。

## 原理与取舍

检索前过滤能避免无权片段进入排序、摘要或提示词；检索后复核则处理索引滞后和权限变化。若底层无法表达完整权限过滤，应采用隔离索引、授权集合约束或其他可证明的方案，不能先把全库结果交给模型再要求它自行保密。

共享缓存必须包含权限域和权限版本，文档被删除或撤权时依赖的摘要与答案也要失效。用户退出部门后，旧会话里已注入的资料不能继续被无条件用于后续回答。授权范围因此需要贯穿历史上下文，而不仅是本轮检索。

工具授权应分为能力级与对象级。agent-orchestration 的 ToolPermission 检查用户权限标签，ToolExecutor 在调用前使用该检查；已读方法没有判断参数中的业务对象归属。它展示的是校验位置，不能替代数据库查询中的租户约束和写操作时的再次授权。

## 实现示例

伪代码：生产设计建议，不绑定具体身份供应商、检索库或仓库接口。

```text
验证访问凭据并建立可信 principal
从服务端授权记录解析 tenant、user、permissionVersion
拒绝请求中的租户与可信租户冲突
按租户和用户可见集合检索文档
对候选片段逐项复核当前访问权后组装上下文
收到工具动作时：
  校验能力权限与参数结构
  在可信租户范围内加载目标对象
  根据对象归属和当前策略再次授权
  对写操作使用事务、幂等约束和必要审批
响应、引用及审计查询继续沿用相同权限边界
```

异步任务要保存可信主体标识，但执行时仍需处理权限撤销。不可仅凭提交时一次授权就无限期放行；高影响动作应在真正执行前重新评估，并保留策略版本作为审计依据。

## 常见坑

- 将 threadId、executionId 或难猜的任务编号当作访问凭证。
- 把缓存命中当作免鉴权理由，同租户不同角色共享私有答案。
- 工具接口信任模型给出的租户或用户字段，绕开可信上下文。
- 仅在前端隐藏按钮，后端查询、历史和审批接口没有相同校验。
- 错误响应泄露另一个租户对象是否存在。

## 验证清单

- 用合成数据覆盖跨租户、同租户跨部门、无角色及已撤权用户。
- 验证检索、缓存、引用、会话历史与工具执行返回一致的权限结果。
- 在排队后撤销权限，确认真正执行时能拒绝旧授权。
- 对读写接口都检查目标对象范围，确认错误响应不泄露无权资源信息。
