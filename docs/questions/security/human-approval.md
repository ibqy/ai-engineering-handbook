# 人工审批怎样绑定真正执行的操作

## 直接回答

审批不能只是给任务设置 approved=true。批准记录必须绑定租户、请求者、工具及版本、目标对象、规范化参数、业务前置条件、有效期和操作标识。执行端只能执行该快照，并在执行前再次检查审批者权限、当前对象状态和批准有效性；金额、收件方或工具参数改变，都要重新申请。

生产设计建议：用持久化状态机管理待审批、已批准、执行中、完成、拒绝和过期，原子消费批准结果，配合业务幂等键。审批解决“允许做什么”，幂等解决“重复到达时不重复做”，二者不能相互替代。

## 实际场景

模型提出报销付款，人看到金额后批准；等待期间数据被修改，若执行时重新读取最新参数，就可能执行人没有看过的操作。另一类问题是确认请求重复或并发到达，一次批准被消费多次，产生重复外部副作用。

agent-orchestration 的 ApprovalGate 保存 taskId、toolName、argsJson 和请求时间，使用进程内 Future 等待，超时按拒绝处理；confirm 方法只接收 taskId。该类没有审批者身份和参数摘要校验，不能把它直接当作完整生产审批凭证。

## 原理与取舍

审批页面应展示服务端保存的操作快照，不接受浏览器提交新的执行参数。对参数先做规范化再计算摘要，避免字段顺序、默认值和数值表示造成歧义；摘要用于检测变化，不证明审批者身份，也不保证内容对人可理解。

数据库中应记录审批者、权限依据、决定、时间、快照版本及审计标识。状态转换采用条件更新或事务，确保同一批准只能进入一次执行流程。实际业务还需唯一幂等键：进程可能在远端成功后、本地记账前崩溃，恢复时应查询既有结果，而不是再次付款。

审批等待期间可能撤权、价格变化或对象已处理。执行前要校验业务版本和授权，冲突时终止或重新审批，不能悄悄调整参数继续执行。检查点恢复只恢复计算状态，无法撤销邮件、付款等外部效果；需要独立的补偿与人工核对流程。

## 实现示例

伪代码：生产设计建议，下面的事务和状态名不是仓库现有 API。

```text
申请：规范化操作参数，保存不可变快照及对象版本
展示：按审批者当前权限读取快照，显示实际影响
批准：记录审批者、快照摘要、有效期和决定
执行：
  开启事务并锁定批准记录
  校验归属、当前授权、有效期、摘要和对象版本
  条件转换 已批准 → 执行中，并登记唯一操作键
  提交事务
  使用相同操作键调用支持幂等的业务边界
  持久化成功结果；未知结果进入核对而非直接重发
```

外部系统不支持幂等时，不能凭本地状态机宣称恰好执行一次。应先评估查询能力、对账和补偿；不可逆的高影响动作在结果不明时优先暂停，并给人工提供可追溯证据。

## 常见坑

- 审批通过后让模型重新生成参数，却继续沿用旧批准。
- 把不可猜测的任务编号当审批身份，或允许跨租户查看待审批内容。
- 超时后默认批准，或将拒绝当普通工具结果让模型继续尝试同一操作。
- 使用内存 Future 作为唯一记录，服务重启后丢失决定和审计链。
- 将“图执行完成”误判为“付款成功”，忽略业务状态和离线模拟标记。

## 验证清单

- 批准后改参数、改对象版本或撤销审批者权限，确认不能按旧批准执行。
- 并发重复确认、过期确认和跨租户确认都应产生可解释结果。
- 在外部成功、本地落账前模拟中断，检查恢复不会重复产生副作用。
- 验证拒绝和超时能终止危险动作，并核对审计记录是否绑定同一快照。
