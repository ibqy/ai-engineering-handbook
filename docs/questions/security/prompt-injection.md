# 提示注入为什么不能只靠一句系统提示防住

## 直接回答

系统提示能告诉模型哪些内容可信，却不能替代服务端权限判断。检索文档、网页、邮件和工具返回都是数据，其中即使出现类似指令的文本，也不应获得更高权限。安全目标不是承诺模型永远不会被影响，而是即使生成错误意图，也无法越权读资料、外发敏感信息或执行危险操作。

本文仅讨论防御。生产设计建议：将提示约束、输入风险识别、资料来源标记、最小权限、工具参数校验和必要的人工审批组合使用，任何单一检测器都不能当作绝对安全证明。

## 实际场景

企业助手读取外部资料后生成摘要，并能调用内部查询工具。资料中的不可信文字可能影响模型下一步选择，但内部工具不应因此扩大查询范围。允许使用工具与允许访问具体业务对象是两件事，后者必须由执行端依据可信身份判断。

已读 ai-platform 的 ContentSafetyFilter 只使用有限正则识别部分输入模式，并对输出进行简单替换。这是教学边界，不能推荐直接上线，也不能称为完备的提示注入防护。其安全笔记关于检测层数与过滤能力的描述和当前源码不完全一致，本文以源码为准。

## 原理与取舍

模型读到的自然语言不应承担授权协议。生产设计建议是先在服务端建立可信身份与允许能力，再将必要资料作为低信任上下文传入模型；文档中的角色描述不能改变服务端权限，模型输出也不能覆盖会话租户。

资料应附带来源、版本和信任等级。检索前限制可见集合，输出前核对引用与敏感字段，工具执行前检查动作、目标对象、参数和外发目的地。不要把内部凭据放进提示词后再依赖模型保密，凭据应由服务端在受控调用边界注入。

规则检测成本可控、便于解释，但会漏报，也会误伤安全研究、代码说明等正常文本。分类器可作为额外风险信号，仍需评估误报漏报和失败策略。内容合规检测与提示注入检测目标不同，不能仅因为服务能审核内容，就宣称能阻断指令混淆。

## 实现示例

伪代码：描述生产防御边界，不是仓库已有的防护接口。

```text
从可信登录态构建用户与租户上下文
按当前权限检索资料，并保留来源与版本
将外部资料作为低信任数据组装，不授予控制权限
若检测结果要求人工核查，则暂停或拒绝
模型提出候选工具动作后：
  校验工具白名单、参数结构、目标对象权限、外发范围
  高影响操作绑定不可变参数快照并请求审批
  仅由服务端执行已授权动作
返回前检查敏感数据与引用权限，记录脱敏审计事件
```

检测超时或结果不确定时应按业务风险选择拒绝、人工处理或只读降级，不能默认为完全可信。只读模式也要限制资料范围，否则“不写数据”仍可能造成信息泄漏。

## 常见坑

- 将“不要泄露信息”写进系统提示后，就把密钥和全库内容一起发送。
- 用正则未命中证明输入安全，或将正常引用误判为攻击后永久封禁用户。
- 只检测用户问题，不检查检索资料、工具输出及后续拼接内容。
- 让模型决定是否允许自己的工具调用，缺少独立的服务端策略。
- 为提高成功率，在检测服务故障时自动放开所有权限。

## 验证清单

- 使用合成且无真实敏感数据的防御样本，覆盖不可信文档影响工具选择的情况。
- 即使模型提出越权动作，也应由执行端拒绝，且拒绝事件能够审计。
- 验证正常资料引用不会被大面积误伤，误报与漏报分开统计。
- 检测不可用、资料缺少来源和引用权限变化时，检查是否进入预定安全分支。
