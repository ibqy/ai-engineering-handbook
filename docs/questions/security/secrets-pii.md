# 日志提示词和检索内容如何保护敏感信息

## 直接回答

先决定哪些数据根本不应进入模型或日志，再处理必须使用的最少字段。密钥只应供服务器受控调用使用，不放进提示词、浏览器、截图或错误响应。个人信息应按用途最小化，并覆盖检索片段、模板变量、工具结果、缓存、追踪、审批快照及备份，而不是只处理用户输入。

生产设计建议：建立数据分类、准入规则、访问控制、保留期限与删除流程。脱敏不自动等于匿名化，残留字段和上下文组合仍可能识别个人；不能仅凭替换部分字符宣称满足所有合规要求。

## 实际场景

客服助手的问题文本已隐藏电话号码，但模板变量包含完整订单联系人，工具异常又把原始请求打到日志。最终回答看起来安全，敏感信息却已在模型供应商、追踪平台与日志索引形成多份副本。

ai-platform 的 PiiMasker 使用三类数字正则并保留末四位，是教学示例。网关仅对 query 调用该方法，模板渲染结果可作为实际消息，因此不能断言完整提示词均已脱敏。agent-orchestration 的 AgentTraceLogger 会截断 thought 与 observation 后记录，截断只是限长，不会可靠移除敏感内容。

## 原理与取舍

应在每个出站与落盘边界重新确认数据用途：发送模型前检查完整组装内容，写日志前选择字段，工具结果进入记忆前去掉无关数据。优先采用字段白名单，例如记录请求标识、工具名称、结果类别和错误码，不默认收集原始问题及完整返回。

必要时用随机代号替换个人标识，映射保留在受控系统，按租户与请求限定访问和寿命。普通哈希不能保证低熵手机号不可推测，掩码也可能让不同人的输入混为一谈；涉及个性化结果时，不应以脱敏后的相同文本直接复用答案。

生产密钥宜由密钥管理设施注入，分环境、分用途授权并支持轮换与撤销。模型供应商是否保留数据、处理区域与训练使用政策需要按实际合同确认，不能从“关闭本地日志”推断第三方不保存。发生泄漏后应停止传播、撤销凭据并按数据治理流程处理副本。

## 实现示例

Java21纯逻辑示例：通过审计事件结构限制默认采集字段，不包含日志框架调用。

```java
record AuditEvent(
    String requestId,
    String tenantReference,
    String actionCode,
    String outcomeCode,
    String policyVersion
) {}
```

这些字段也需校验格式与长度，租户引用仍可能属于受保护元数据。生产异常处理应输出受控错误码，内部诊断详情单独授权；禁止为了方便排查，把原始提示词或凭据塞进 actionCode 等字段规避白名单。

## 常见坑

- 认为日志截断、关闭一个客户端日志开关或输出打码就覆盖整个链路。
- 正则处理失败或文本过长时直接透传原文，造成保护失效时反而泄漏。
- 把提示词、检索片段和工具响应全量放进追踪属性。
- 只删除主库记录，忘记缓存、向量索引、历史快照及备份保留策略。
- 在排查问题时将真实密钥或客户记录复制到聊天、工单与截图。

## 验证清单

- 用合成敏感数据覆盖输入、模板变量、检索、异常和流式输出路径。
- 检查应用日志、代理日志、追踪、缓存键值及审批记录是否出现原值。
- 演练密钥轮换、撤销与数据删除，核对是否还有不可控副本。
- 对脱敏失败、超长输入及无法识别的数据类型验证拒绝或人工处理策略。
