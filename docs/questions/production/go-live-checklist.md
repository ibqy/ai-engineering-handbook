# AI应用上线前最少需要哪些验收

## 直接回答

最少需要六类证据：业务答案与拒答质量、身份及数据权限、敏感信息保护、费用与容量限制、任务生命周期和故障恢复、发布回滚与值守处置。每项应记录环境、版本、输入、期望、实测结果和负责人。没有证据就是未验证，不应通过填“正常”或展示成功截图完成验收。

以下清单是生产设计建议，不代表三个参考仓库已有相应保障。阈值应由实际用户体验、业务风险与预算共同制定，本文不提供未经测量的性能数字或通过率。

## 实际场景

内部助手在开发机能回答问题，上线后多个部门接入，资料权限、供应商限流和后台任务重启才成为关键问题。即使暂时只读，也可能泄漏内部信息或持续消耗费用；“没有写操作”不能免除授权和成本验收。

ai-platform 的示例前缀鉴权、正则注入检测、ConcurrentHashMap 缓存以及本地线程队列均是教学边界，不能推荐直接上线。LangGraph4j 边界文档也明确本地接口、内存检查点和模拟支付不构成生产平台。验收必须先识别这些差距，而不是只检查服务能启动。

## 原理与取舍

按最小上线范围选择证据深度，但不能省略安全底线。先限定用户群、允许资料、工具集合与费用上限，再逐步开放。高影响工具需要对象级授权、绑定参数的审批和幂等处理；无工具的问答应用仍需检索权限、敏感数据控制及引用验证。

可靠性验收要观察故障后的业务状态，而不只是异常是否被捕获。任务提交、出队、外部执行与结果落库之间都可能中断，必须说明是否可恢复、是否可能重复和谁负责核对。SSE 断开还需区分取消执行与取消观察者，避免任务泄漏或误杀。

运行保障应有脱敏监控、故障告警、费用告警与人工兜底。模型、模板、知识快照和协议版本应可追溯；回滚方案要考虑旧索引、旧会话、等待审批任务和无法撤销的副作用。健康接口返回成功，不等于模型可用，更不代表业务答案正确。

## 实现示例

伪代码：验收门禁记录，字段是设计示意，不是仓库现有发布接口。

```text
验收项 = {
  范围与风险,
  受测版本与环境,
  输入及预期结果,
  实际执行证据,
  责任人与复核人,
  阻断条件及处置方式
}
发布条件：全部必要项有证据，阻断项为零
灰度异常：停止扩大流量，保留诊断证据并按预案回退
未知结果：明确标为未验证，不自动视为通过
```

门禁应保存原始失败样本和复核决定，避免重跑成功后抹掉偶发问题。对于暂不开放的能力，应从服务端关闭入口与权限，而不是仅在说明文档里声明“不建议使用”。

## 常见坑

- 将单元测试、启动成功或历史文档中的测试记录当成本次完整验收。
- 未核实真实模型调用和用量字段，就按示例估算给用户结算。
- 只有成功率监控，没有取消残留、越权拒绝、队列积压及成本告警。
- 有回滚按钮却无可恢复的旧依赖，也未安排故障负责人。
- 为方便接入直接公开教学接口，寄希望于任务编号不被猜到。

## 验证清单

- 质量：代表性问题、无答案问题、引用与工具参数都有样本级结果。
- 权限：跨租户、跨角色、撤权后的检索、缓存、历史和工具访问均受控。
- 数据：输入、模板、日志、追踪、缓存及备份符合最小化与保留策略。
- 成本：记录真实尝试链，预算预占、重试上限、限流与对账可验证。
- 可靠性：断线、超时、重启、重复提交和部分成功都有明确终态与恢复路径。
- 发布：版本可追溯，灰度可停止，回滚已演练，告警能到达实际值守人员。
