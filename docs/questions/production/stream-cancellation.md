# SSE断开后为什么后台任务还在跑

## 直接回答

SSE 是输出通道，不天然拥有后台线程、模型请求和工具任务的生命周期。浏览器断开后，服务端可能还没察觉；即使发送失败，也可能只关闭响应而不停止生产者。应先定义连接是“创建并拥有一次执行”，还是“观察已存在任务”，再决定断线是否触发取消。

生产设计建议：连接拥有的执行需要将断线、超时和显式取消汇入幂等终态处理，并向工作线程、子任务、排队等待和底层调用传播。仅有 Future 进入取消状态，不等于执行已停止，也不等于供应商停止计费。

## 实际场景

ai-platform 的 AiGatewayController 在虚拟线程提交流式处理，没有保留提交返回的 Future。发送回调遇到 IOException 时只调用 completeWithError，没有向外传播取消信号，也未注册完成、错误和超时回调。因此不能从连接关闭推断后台循环终止。

相比之下，已读 LangGraph4j 的 DemoRuntime 会登记连接回调、取消标记、生成器、节点动作及所属线程，并在消费时检查取消。这展示了更完整的本地生命周期处理，但仍不能承诺真实外部服务立即停止或副作用自动撤销。

## 原理与取舍

取消需要协作：调度前检查、等待中可中断、每个阶段边界复查、终态后禁止再发布成功。注册工作句柄与触发取消还存在竞态，不能先取消再登记一个新任务后让它继续运行。资源清理应幂等，重复的断线、超时与发送异常只能完成一次终态转换。

普通 Future、线程中断、异步流取消与网络请求中止是不同层次。尤其 CompletableFuture 的取消不能被当成通用线程中断保证；第三方客户端是否支持中止需要按实际实现验证。不能响应中断的调用应设置有限超时并限制并发，记录取消后的残留工作。

若 SSE 仅订阅持久任务，某个观察者断线通常只应取消订阅；否则多端查看时，一个页面关闭就会杀掉所有人的任务。生产设计应另设经过授权的任务取消动作。审批暂停后的连接结束也不应取消后来恢复的执行。

## 实现示例

伪代码：连接拥有执行时的生产设计建议，不是框架取消 API。

```text
创建执行时建立取消状态和所属资源集合
注册连接错误、超时及非正常结束处理
登记工作句柄；若已经取消，立即取消该句柄
每次调度、等待结束和输出前检查取消状态
取消时原子转换运行态为取消处理中
停止新增任务，通知子任务与底层请求，释放等待
确认本地资源回收后记录取消终态
若外部结果未知，保留待核对记录而非宣称撤销成功
```

正常完成回调也可能在关闭连接时触发，因此需要区分正常终态与异常离开。最后清理应取消计时器和订阅，避免过期回调在后续恢复时影响新执行。

## 常见坑

- 捕获发送异常后继续生成并计量，连接关闭只是隐藏了输出。
- 只取消消费循环，没有管理并行分支、嵌套图或外部调用。
- 将取消任务等同于撤销已执行的订单、邮件或支付。
- 无限缓存慢客户端未消费的片段，缺少背压与队列上限。
- 用节点事件冒充模型 Token 流，再声称验证了真实模型断线行为。

## 验证清单

- 分别在排队、模型等待、工具执行和最终输出时断线，观察实际剩余工作。
- 模拟底层忽略中断，确认有限超时、并发保护和残留告警生效。
- 检查多订阅者断线只移除对应观察者，不误取消持久任务。
- 在取消与完成并发时验证唯一终态，并核对费用、线程及子任务是否继续增长。
