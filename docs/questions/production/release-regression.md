# 模型提示词知识库更新怎样灰度与回滚

## 直接回答

不要把模型、提示词和知识库分别切到“最新”后再猜测回归来自哪里。应建立不可变发布清单，包含实际模型标识、模板版本、知识快照、检索配置、工具协议与安全策略；每次请求固定一份清单并记录实际执行值。灰度按稳定分组逐步扩大，回滚切换完整兼容版本而非只换一个模型名称。

以下发布流程是生产设计建议。仓库中的版本存储和哈希分流只是教学机制，不等于具备发布审批、自动回滚或跨实例一致性保障。

## 实际场景

知识库修订后，旧提示词仍要求引用已删除字段，模型本身没有变化却开始答错。若缓存键也没包含模板版本，灰度组可能一直读取旧答案，造成“更新没有影响”的假象。

ai-platform 的 PromptTemplateStore 支持指定版本和租户哈希选择首个或最后保存的版本；getLatest 的含义是最后保存，不是语义版本比较。它使用 ConcurrentHashMap 保存可变列表，不能据此宣称发布写入与读取是完整原子快照。网关缓存也未包含模板版本，需要单独处理。

## 原理与取舍

先固定离线评测集，覆盖正确答案、证据引用、应拒答问题、权限边界与工具参数，再运行受控真实依赖验证。评测样本应与调参样本分离，防止只优化已知题。模型输出具有波动，重要样本需要重复观察并保留失败实例，而不是仅看一轮平均分。

灰度分组可按租户或会话稳定映射，但用户比例不等于流量比例，大租户可能主导费用和负载。对比时应分场景观察质量、首字延迟、总耗时、成本和错误类型；回滚触发条件由业务目标确定，不能虚构统一阈值。

旧知识快照、模板和检索索引要在回滚窗口保留，权限撤销与数据删除则不能因回滚重新放开。长会话及等待审批任务应固定兼容版本或走显式迁移，避免恢复时工具协议已改变。影子流量必须禁止真实写副作用，并控制敏感数据外发与额外费用。

## 实现示例

Java21纯逻辑示例：只表示不可变发布清单，不提供配置中心或灰度服务 API。

```java
record ReleaseManifest(
    String releaseId,
    String modelVersion,
    String promptVersion,
    String knowledgeSnapshot,
    String retrievalVersion,
    String toolSchemaVersion,
    String safetyPolicyVersion
) {}
```

生产执行中应记录这份清单与实际使用版本的差异，并将影响答案的字段纳入缓存身份。开始请求后不应每个阶段重新读取“最新版本”；回滚发布指针时也要检查旧依赖仍可用及安全策略是否允许。

## 常见坑

- 路由选择了新模型名称，就认定真实请求已发往对应模型，缺少执行核对。
- 灰度期间共享答案缓存，导致新旧组互相污染，评测失真。
- 只保留新版知识索引，故障时名义回滚但旧版本无法执行。
- 把恢复检查点当作撤销已发送邮件或已付款操作。
- 回滚旧配置时重新启用已撤销权限或不合规资料。

## 验证清单

- 对每个响应追溯模型、模板、知识快照和检索配置的实际版本。
- 固定同一评测集比较新旧发布，保存样本级差异及拒答原因。
- 验证稳定分流、缓存隔离和回滚后的真实依赖可用性。
- 检查长任务、审批恢复和旧状态迁移，确认协议兼容与权限有效。
- 演练完整回滚并核对未完成副作用，不能只观察配置按钮成功。
