# 写操作超时后怎么防止重复执行？

## 直接回答

超时不等于失败，更不等于“没有执行”。服务可能已经写入，只是返回途中断线。防重的关键是为一次经过确认的业务意图分配稳定幂等键，由服务端持久化处理状态和结果；同一意图重试复用原键，不让模型每次生成新键。

幂等键应绑定租户、动作和业务意图，同时保存规范化参数摘要。同键同参数返回已有状态，同键不同参数拒绝。用户确实要再次购买同一商品时属于新意图，不能仅用参数哈希永久去重。

## 实际场景

用户确认退款后，工具请求超时。模型再次提出退款调用，若后端只看订单与金额就新建退款单，会造成重复申请。正确响应应是“结果待确认”，并按原操作编号查询；确认失败且允许重试时，仍使用同一个幂等键。

模型提供的工具调用编号通常只是一次对话协议关联信息，不一定在跨轮重试中稳定。应用应保存“用户确认记录—业务意图—幂等键—下游流水号”的关系，让恢复流程不依赖模型记忆。

## 原理与取舍

同库写操作可在事务里创建唯一幂等记录、修改业务数据并保存结果。并发请求靠数据库唯一约束竞争，而不是先查后写的内存判断。进程崩溃后也要能读回状态，保留时间应覆盖业务重试和对账窗口。

跨服务或支付通道无法用本地事务包住所有效果。应把同一幂等键传给支持幂等的下游；否则借助持久化任务、操作查询和人工对账恢复。收到超时后保留未知状态，不应直接标记失败并释放键。租约过期也不能证明旧执行者没有成功，重新接管前必须核实下游状态。

重试只针对可重试故障，次数与退避均受预算约束。补偿也可能产生新的副作用，应有自己的幂等语义；“先重复执行，再自动撤销”不等价于安全。

## 实现示例

伪代码：数据库事务和下游能力是设计前提，不是现成框架 API。

```text
接收 tenant + intentKey + 参数摘要
原子创建或读取唯一幂等记录
if 已有记录且摘要不同: 拒绝冲突
if 已完成: 返回保存的业务结果
if 正在处理或结果未知: 返回原操作编号供查询
若本请求获得首次执行权:
    持久化待执行任务与业务意图
    使用同一 intentKey 请求下游
    若明确成功: 保存下游流水号和最终结果
    若超时: 标记结果未知，转查询与对账
```

保存任务与本地业务状态时要使用一致的事务边界。示例刻意没有“超时就重置为未执行”分支，也没有承诺跨系统恰好一次；最终正确性依赖下游去重、状态查询或可审核的恢复流程。

## 常见坑

- 用线程安全集合代替幂等，它只能保护容器操作，不能识别重复意图。
- 以会话编号去重整个会话，误阻止用户的第二次合法操作。
- 删除未知状态后重试，导致第一次执行的迟到结果无法关联。
- 让模型自行决定付款是否成功，再据此更新数据库。

## 验证清单

- [ ] 同键并发提交只形成一次业务效果，参数变化被拒绝。
- [ ] 在写入后、响应前注入断线，重试能返回原结果。
- [ ] 模拟进程重启和下游慢返回，未知状态不会盲目重放。
- [ ] 新意图可正常执行，过期策略与对账窗口一致。
