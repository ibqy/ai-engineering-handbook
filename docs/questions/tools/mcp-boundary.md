# MCP 与普通 API、工具调用是什么关系？

## 直接回答

三者解决不同层的问题。普通业务 API 提供查订单、查库存等服务；工具调用让模型用工具名和参数提出请求；MCP 则为 AI 应用与外部能力之间提供标准化交互边界。一个 MCP 工具内部可以调用 HTTP API，也可以执行本地方法。已有可靠 API 不必为了“智能化”全部重写成 MCP。

本文聚焦 MCP 的工具能力，不将其等同于协议全部功能。MCP 服务端不是模型本身，也不会因为采用协议就自动获得用户授权、业务幂等或可靠性保证。

## 实际场景

公司已有订单服务，单个客服应用只调用两个端点时，直接包装成本地工具通常足够。若多个不同 AI 客户端要复用同一批业务能力，可以考虑用 MCP 服务端统一发布工具描述和调用入口。

此时边界是：客户端发现工具，应用决定本轮允许哪些工具，模型提出调用，客户端转发至 MCP 服务端，服务端再请求订单 API。排错要沿这条链逐段定位，不能把 API 的无权限错误简单归因于模型“不聪明”。

## 原理与取舍

统一协议降低重复适配成本，同时增加服务连接、能力发现、版本兼容和凭据管理的工作。少量同进程工具无需强行远程化；跨团队复用更需要清晰的契约和发布责任。

工具发现不等于授权。即使服务端公布了删除工具，当前用户也未必可以调用。客户端应按会话过滤候选，服务端仍需核验身份和对象权限；后端 API 继续执行原有鉴权，不能因为请求来自 MCP 就跳过检查。

本地进程与远程服务的运维边界也不同。本地进程受操作系统账号、文件目录和环境变量权限影响；远端连接则需明确传输保护、凭据生命周期、网络访问范围和调用超时。采用哪种部署方式，应根据实际使用的协议与实现版本验证，不能照搬某个演示配置。

## 实现示例

伪代码：为已有订单 API 增加工具适配层，不代表 MCP SDK 的实际方法签名。

```text
发布工具 order_query:
    输入模式只包含 orderId
    描述为“查询当前用户有权访问的订单”
收到调用:
    验证客户端身份与当前用户授权
    校验 orderId 并检查调用配额
    使用受控凭据请求订单 API
    保留业务错误类型与追踪编号
    只返回回答所需字段，不返回内部令牌
客户端:
    仅把本会话允许的工具交给模型
```

适配层不应把后端所有字段原样透传，也不应将所有失败都包装成自然语言“没有订单”。区分不存在、无权限、限流和暂时不可用，才能选择正确的追问或重试策略。

## 常见坑

- 把工具服务地址当成模型端点配置，混淆调用方向。
- 默认信任服务端返回的描述或内容，让外部文本改变系统权限。
- 将开发机整个目录暴露给文件工具，只靠提示词限制读取。
- 以为迁移到 MCP 就同时解决了重复写入、审批和事务一致性。
