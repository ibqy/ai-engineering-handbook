# 工具太多导致误选怎么解决？

## 直接回答

不要先让模型读完全部工具，再追加一句“务必选对”。先按用户权限、业务域、任务阶段和参数条件筛出候选，只提供当前真正可用的工具；再明确工具名称、适用意图、必要参数以及禁止用途。候选筛选是提高选择质量的措施，执行端仍要独立鉴权。

对同一件事提供多个近义工具，会让选择问题变得含糊。应统一业务语义，或者清晰区分查询、预览、提交和取消，而不是让模型从内部系统名称猜用途。

## 实际场景

客服接入查订单、查物流、查退款规则、申请退款、撤销退款和修改收货地址。用户问“退货政策是什么”却被选成申请退款，可能不是模型不够强，而是工具描述都写了“处理退货问题”。

可以先限定为政策咨询阶段，只暴露只读能力。用户明确要求申请后，再收集订单号并查询资格；得到确认记录后，服务端才开放提交入口。状态由应用保存，不由模型自报“用户已经确认”来推进。

## 原理与取舍

常用方式有规则筛选、领域路由和工具检索。规则最可控，适合固定流程；领域路由减少候选，但多领域请求可能被错分；工具检索适合较大的工具目录，却可能漏掉低频关键工具。因此需要保留追问与重新路由通道，不能在候选为空时随便选最相似工具。

工具描述应写“何时用、何时不用、需要什么”，返回模式则区分成功、无结果和业务拒绝。不要把多个用途塞进一个万能字符串参数，也不要为了细粒度把同一业务动作拆成一串容易跳步的底层操作。

评估要同时看候选召回率与最终选择正确率。如果正确工具根本没被筛入，优化最终提示词没有意义。误选矩阵能揭示哪些工具相互混淆；对危险写操作的误调用应单列指标，不能与普通查询误选平均处理。

## 实现示例

Java21纯逻辑示例：用已确定的业务域与授权范围过滤，不实现意图识别。

```java
record ToolMeta(String name, String domain, String permission,
                boolean writes) {}

static java.util.List<ToolMeta> candidates(
        java.util.List<ToolMeta> catalog, String domain,
        java.util.Set<String> grants, boolean confirmed) {
    return catalog.stream()
        .filter(t -> domain.equals(t.domain()))
        .filter(t -> grants.contains(t.permission()))
        .filter(t -> !t.writes() || confirmed)
        .toList();
}
```

这里的 `confirmed` 必须来自服务端且绑定具体动作和参数，不能是模型给出的布尔值。即便候选中有写工具，执行前也要核对确认范围、对象权限和当前状态；候选列表不应跨用户缓存复用。

## 常见坑

- 工具数量限制得很小却没有测候选召回，正确工具经常被过滤掉。
- 通过重命名掩盖重复能力，后端仍保留相互冲突的业务定义。
- 工具不存在时让模型猜名称，产生无法分派的调用。
- 把最大循环次数当成选对工具的保证，它只能限制失控成本。

## 验证清单

- [ ] 有跨领域、模糊意图、信息不足和无需工具的测试样本。
- [ ] 记录候选工具、最终选择、参数正确性及执行结果。
- [ ] “问规则”与“提交申请”等相邻意图不会混用。
- [ ] 低召回时能追问或重新路由，不自动放开全部危险工具。
