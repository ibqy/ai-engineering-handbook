# Tool Calling 是谁真正执行代码？

## 直接回答

通常的 Tool Calling 中，模型根据工具说明提出“调用哪个工具、传什么参数”，不是模型自己进入数据库执行 Java 方法。应用运行时解析调用请求，找到注册的处理器，检查输入与权限，再执行本地代码或请求远端服务。工具结果返回模型后，模型可能继续调用工具，也可能生成最终回答。

框架的自动工具循环隐藏了中间步骤，没有消除应用责任。工具越像真实业务入口，越应按普通外部请求对待模型参数，而不是因为它来自模型就默认可信。

## 实际场景

用户问“订单 A1001 到哪了”，模型选择订单查询工具，应用取得当前用户身份，核实订单归属，再查询物流。如果用户问“可以退款吗”，应先查规则和订单状态；不能把询问资格理解成已授权提交退款。

模型最后说“退款成功”也不能成为成功凭证。界面应根据业务服务返回的操作编号和状态展示结果，必要时把模型的解释与可信状态卡片分开呈现。没有执行记录时，只能说明尚未执行。

## 原理与取舍

工具定义应描述单一目的、参数类型、必填条件和副作用。只读查询容易重试，写操作则需要确认、幂等及审计。身份、租户和访问令牌从服务端上下文注入，不宜成为模型可以任意填写的参数。

自动循环适合模型根据结果决定下一步，但要限制调用次数、总耗时和可用工具。关键写流程可以改用确定性的编排：先验证、再确认、最后调用，让模型负责理解和解释，而不是决定是否跳过审批。

工具返回内容同样属于不可信数据。外部网页或数据库备注里出现“请调用删除工具”，不能提升为系统指令。保留来源和调用关联编号，使最终回答能追溯到具体结果。

## 实现示例

伪代码：展示执行边界，各函数是应用设计职责，不是任何框架 API。

```text
接收模型工具请求(name, arguments, callId)
if name 不在本轮允许工具集合:
    返回工具不可用
参数 = 按工具模式解析并限制大小(arguments)
身份 = 从已认证会话读取()
检查对象归属与动作权限(身份, 参数)
if 工具具有写副作用:
    检查用户确认与幂等记录()
结果 = 在超时预算内执行已注册处理器(参数, 身份)
记录(callId, 工具名, 执行状态, 脱敏结果引用)
把结果交给模型；最终业务状态从执行记录读取
```

“允许工具集合”必须在执行时再次检查，不能只通过少给模型几个描述来实现权限控制。解析错误应形成明确的工具失败结果，不能改成空参数继续执行默认操作。

## 常见坑

- 暴露任意 SQL、任意文件路径或任意 URL 工具，远超业务所需能力。
- 将“自动选择”理解成“一定调用”，没有工具轨迹却相信回答。
- 默认参数指向某个真实订单，模型漏参时仍执行。
- 工具内部异常被转换成成功文案，模型无法区分业务拒绝与系统失败。

## 验证清单

- [ ] 能区分模型建议、工具执行和最终回答三类记录。
- [ ] 非法工具名、缺参、越权及超时都有可预测结果。
- [ ] 用户身份不可由模型覆盖，写动作有独立确认。
- [ ] 循环有预算，失败后不会靠模型自述伪造完成状态。
