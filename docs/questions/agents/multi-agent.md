# 多Agent什么时候有用什么时候徒增成本

## 直接回答

多 Agent 适合可分解、有清晰交付物、需要不同工具或权限边界的任务，不适合把同一道简单问题反复交给几个相似提示词。先证明单 Agent 或固定工作流不足，再评估并行收益、质量提升是否覆盖计划、通信、评审与重试成本。

角色数量不等于独立判断数量；多个角色共享模型和错误证据时，可能只是重复同一种偏差。

## 实际场景

研究任务可拆成法规核对和技术资料调查，两者独立取得证据后再汇总。若最终报告依赖二者结论，汇总节点必须等待依赖完成，并知道每份结果的来源和版本。

若只是查询一次库存再生成回复，额外加入 Planner、Worker、Reviewer 通常只增加模型往返。对于资金操作，应按权限拆分，而不是让更多角色都获得付款能力；评审角色原则上只读，真正执行由授权工具完成。

## 原理与取舍

agent-orchestration-demo 的 TaskPlan 根据已完成任务 ID 筛选可运行任务，编排器按批次交给 BatchRunner，遇到无可运行任务时退出并汇总。调度上等前置完成，不等于前置结果已经进入后续提示词：Worker 实际只把当前子任务目标传给推理 Agent，不能凭依赖边推断自动完成了证据传递。

BatchRunner 使用虚拟线程和 CompletableFuture 聚合，超时或失败时取消其他 future。但 future 被标记取消，不证明底层工具或远程请求已停止，更不代表副作用回滚。Worker 把普通异常转成任务失败结果，因此也不能断言所有业务失败都会触发批次异常快退。

评审循环有具体边界：首次执行后最多两次 RETRY；第二次重试执行完即跳出循环并标记失败，没有第三次评审机会。这个教学实现不等价于“每次重试成功都能获准”。生产应明确次数含义，并测试最后一次尝试的验收逻辑。

## 实现示例

以下是建议的伪代码，不是对仓库现有接口的调用：

```text
# 伪代码
校验计划：任务ID唯一、依赖存在、无环、总预算可接受
选择依赖已成功的任务，并传入明确的证据产物
按并发额度运行，每项输出状态、来源和成本
若前置失败：标记依赖阻塞，不能伪造成功
若需要重试：先确认动作可重放，再预占剩余预算
汇总时保留失败项与缺失证据，不只拼接自然语言
```

输出契约应有稳定产物 ID、版本及证据引用；共享状态尽量只合并增量。对有副作用的任务，重复执行前核对幂等记录，而不是由 Reviewer 的一句 RETRY 直接重发操作。

## 常见坑

把虚拟线程等同于无限并发，会撞上模型限流和成本上限。只统计 Worker token 会遗漏规划、评审和返工开销。将部分失败汇总成一段通顺文本，再给任务标成功，会掩盖未完成目标。

图上有并行边不等于已证明运行重叠；测试应使用同步门控检查两分支都进入，而不是只看最终结果列表有两项。

## 验证清单

- 在同一任务集上比较固定流程、单 Agent 和多 Agent。
- 同时记录任务成功、证据覆盖、总调用成本及尾延迟。
- 检查依赖环、前置失败、最后一次重试和人工拒绝。
- 超时后观察是否仍有工具运行或外部写入。
- 检查上下文传递、角色权限和共享状态竞争。
