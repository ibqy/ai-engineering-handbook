# 何时用确定性工作流何时用Agent

## 直接回答

先问“下一步由谁决定”，而不是“有没有调用大模型”。若步骤、分支和审批条件能够预先列清，用确定性工作流；若必须根据工具返回的信息动态选择下一步，才考虑 Agent。工作流里的文本生成可以不确定，但它的控制路径仍由程序约束。两者可以组合，不必把整条业务链都交给模型。

## 实际场景

退款客服适合“分类、找规则、写草稿、人工审批、结案”的固定骨架。Spring AI Alibaba 图示例的工单流程正是如此：关键词决定退款或咨询分支，文本生成器只写回复，审批布尔值决定结案或退回。它使用本地资料，不连接真实工单系统，也不实际退款。

相反，排查未知故障可能需要先查指标，再依据结果查询日志或配置，工具选择无法完全提前枚举。此时可以把诊断部分做成 Agent，但停服、删数据等动作仍应进入确定性的授权节点。

## 原理与取舍

工作流把决策空间压缩为显式节点和条件边，容易覆盖异常路径、计算成本上界，也容易说明为什么进入某个分支。代价是需求变化时需要修改规则，开放问题可能产生很多分支。

Agent 把一部分决策交给模型，通常以“模型输出、工具执行、观察回填、再次决策”循环推进。LangGraph4j 的模型工具示例检查响应是否包含工具请求：有请求就进入工具节点，否则结束。因此，使用图框架并不意味着一定是固定流程；反过来，出现模型节点也不意味着已实现自主规划。

选择时还要考虑错误代价：探索式查询可以允许试错，资金和权限变化则需要更窄的动作集合。模型建议与业务授权应分离，工具参数仍须程序校验。先建立简单基线，再用同一任务集衡量自主决策是否带来净收益。

## 实现示例

下面是 Java21纯逻辑示例，只表达边界，不依赖图框架 API：

```java
// Java21纯逻辑示例
record Ticket(boolean evidenceReady, boolean approved) {}
enum Next { COLLECT, REVIEW, CLOSE }
final class Routing {
    static Next next(Ticket ticket) {
        if (!ticket.evidenceReady()) return Next.COLLECT;
        return ticket.approved() ? Next.CLOSE : Next.REVIEW;
    }
}
```

这里的批准值应来自可信审批记录，而不是从生成文本中提取“同意”二字。真实服务还要验证审批人、对象版本和操作范围。示例故意不执行外部写入，避免把路由判断误写成安全授权的完整实现。

## 常见坑

把多个固定提示词串联后称为“自主 Agent”，容易高估系统能力；为了追求灵活性让模型决定所有路由，又会丢失可测试边界。另一个误区是以图画得复杂证明执行能力：节点是否真的并行、是否在审批前暂停，都应通过执行和测试验证。

离线文本模板只能验证流程连接，不能证明真实模型理解准确；本地关键词检索也不能被包装成向量检索效果。

## 验证清单

- 每条路径是否有成功、失败、缺资料和拒绝审批的明确出口？
- 固定工作流与 Agent 是否用相同业务样本比较成功率、调用数及人工接管率？
- 模型能否绕过审批，或者通过输入覆写内部状态？
- 离线测试、真实依赖测试和模型质量评测是否分别报告？
- 从试验走向生产前，是否补齐鉴权、幂等、超时及审计？
