# 有检查点为什么不等于安全恢复

## 直接回答

检查点描述“图执行到哪里、保存了什么状态”，不自动保证进程重启后可读、不保证恢复权限，更不保证外部动作只发生一次。安全恢复必须同时回答：状态能否可靠保存，恢复位置是否正确，谁有权恢复，重复执行会不会产生副作用。

MemorySaver 是内存检查点，不是跨重启持久化。即便换成持久化存储，也仍需解决业务事务与检查点之间的失败窗口。

## 实际场景

审批后调用支付接口，银行已扣款，但应用在保存“已支付”之前崩溃。恢复时看到旧检查点，再执行支付节点便可能重复扣款。反过来，先写“已支付”再调用银行，崩溃则可能留下未支付却显示成功的状态。问题不是多保存几次检查点就能消除。

教学项目的状态内余额加法和模拟凭证可用于讲解防重，但没有真实银行事务，不能以其测试结果宣称分布式恰好一次执行。

## 原理与取舍

LangGraph4j 运行器在审核节点前中断；恢复时先检查 WAITING_REVIEW，取得最新快照，更新审批字段，再使用恢复输入继续。它还用执行级锁防止同进程并发恢复。这里不是把最初输入重新跑一遍，也不是把旧检查点标识永久缓存后重复使用。

Spring AI Alibaba 的人工审批示例显式注册恢复字段的状态策略。字段普通运行时能读取，不代表恢复时必然被正确装载；序列化与合并策略也是恢复协议的一部分。对应测试检查两级审核与重复审批，但单进程测试不覆盖跨实例争抢。

另外，快照查询不等于续跑。agent-orchestration-demo 的 query 仅加载任务快照，人工确认是唤醒当前等待执行；这些方法不能证明进程重启后能重建完整计划。生产还需持久化调度信息、版本校验、抢占租约及故障演练。

## 实现示例

下面是伪代码，仅表达外部幂等协议，不假设数据库与支付系统共享事务：

```text
# 伪代码
以稳定业务键创建操作记录，唯一约束拒绝重复创建
若已有成功凭证：直接复用结果
若已有处理中记录：先查下游状态，不盲目重发
调用支持同一幂等键的下游接口
保存下游操作编号和结果，再推进图状态
若响应丢失：通过操作编号或幂等键查询并对账
```

本地事件发布可考虑事务发件箱；不支持幂等或查询的下游，应设计补偿和人工对账。幂等键要绑定业务意图及参数，不能每次恢复都生成新键。回滚图状态也不会撤销已发送邮件。

## 常见坑

把 executionId 当认证凭证；允许调用者任意覆写审批字段；只保存结果而遗漏下一节点、计划版本和预算；恢复旧版本图时不迁移状态，都是常见隐患。锁只在单实例有效时，还要防止多实例同时恢复。

取消请求也不是副作用回滚。应记录“请求已发送但结果未知”，不要因为流断开就把它伪装成从未执行。

## 验证清单

- 在外部调用前、成功后、检查点写入前后分别注入故障。
- 验证重启、跨实例、重复审批与旧版本状态的行为。
- 核对审批身份、业务对象版本和稳定幂等键。
- 验证保存失败时的处理策略及对账入口。
- 区分快照可查询、节点可续跑与业务可安全恢复。
