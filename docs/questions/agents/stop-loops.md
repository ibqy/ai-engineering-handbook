# Agent反复调用工具怎样退出

## 直接回答

给 Agent 同时设置正常完成条件和强制退出条件：有效答案、步数上限、工具调用预算、总截止时间、重复动作以及人工拒绝。最关键的是终止信号必须被调度层识别，停止后续模型和工具调用，并返回“未完成”等明确状态；在观察文本中写“强制终止”，不等于循环已经结束。

## 实际场景

客服查询不到订单，模型连续用相同参数查同一工具。应先判断观察是否回填：如果结果根本没有进入下一轮上下文，增加提示词不能解决问题。若观察完整但模型仍重复，则应允许有限次修正，之后转人工或解释缺少什么资料，而不是继续消耗预算。

ReActAgent 的源码会把工具结果追加到上下文，并用最大步数限制循环；格式解析失败也占用一步。LangGraph4j 的工具示例另有六轮模型调用上限，超过时抛异常。它限制的是模型轮数，不能直接当成工具调用总次数。

## 原理与取舍

要区分三种机制。软反馈给模型纠错机会；硬限制由程序阻止继续调度；取消则尝试停止已开始的工作。后两者也不意味着外部请求已经撤销。总耗时上限和每次调用超时都需要，否则单次阻塞就可能绕过步数控制。

agent-orchestration-demo 的 LoopBreaker 返回字符串，调用方遇到非空结果直接把它作为工具观察返回。因此该次真实工具执行被挡住，但 ReAct 仍可能继续调用模型。不能把错误文本里的“任务强制终止”当作控制流事实。

它的重复检测使用工具名和原始参数字符串的哈希，并检查保存的近期签名是否全部相同。JSON 键顺序不同可能漏检，哈希也可能碰撞；窗口混入其他签名时，更不能把实现简化成精确的“第三次必停”。生产建议先规范化参数，再结合进展指标判断重复，避免误伤正常轮询。

## 实现示例

以下是伪代码，描述建议补齐的调度协议，并非仓库现有 API：

```text
# 伪代码
每轮开始：检查截止时间、取消信号和预算
若触发硬限制：保存 LIMIT_REACHED，返回未完成
请求模型并校验输出
若为有效最终答案：保存 COMPLETED，返回答案
若为工具请求：原子预占预算，检查权限与重复签名
若检查拒绝：保存明确终态，不再调用模型
执行带超时的工具，将结构化观察回填
```

并发 Worker 应共享任务级预算并原子扣减；否则各自未超限，合计却超支。保留停止原因、最后安全状态及已发生副作用，方便人工接手。

## 常见坑

把“请换参数”当成硬熔断，会让无效尝试持续到其他上限。返回“任务未完成”的普通字符串，也可能被上层当成正常成功结果：仓库 Worker 在 Agent 正常返回后就标记 DONE，不能仅凭这个状态判断业务完成。

无限重试解析错误、只限制成功调用、在副作用发生后才查预算，同样会造成失控。高风险工具的重复执行不能仅靠循环检测，还需要业务幂等。

## 验证清单

- 连续相同调用、交替调用、参数重排和无效输出是否都能有限退出？
- 终态之后是否再无新的模型或工具调度？
- 超时、人工拒绝和预算耗尽是否保留不同原因？
- 并发预算是否原子，恢复后是否继续累计？
- 已发出的外部操作是否能查询或补偿？
