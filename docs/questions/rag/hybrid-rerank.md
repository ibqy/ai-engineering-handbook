# BM25向量RRF与Rerank如何配合

## 直接回答

建议把职责拆成四段：BM25 寻找词面匹配，向量检索寻找语义相关内容，RRF 合并两路排名，Rerank 对候选逐对重新判断相关性。最后还要去重并按上下文预算选证据。候选里没有答案，重排不能把答案创造出来。

这是建议的集成方式，不是仓库现状声明。当前 `HybridSearchService` 顺序调用两路检索后执行 RRF；`RagController` 直接组装融合结果，未调用已有的 `RerankService`。

## 实际场景

技术支持同时面对“错误码 E1042 怎么处理”和“服务一直启动不了”两类问题。前者需要保留编号的区分度，后者需要识别改写。两路互补是否有效，要在这两类问题上分别观察，而不是只看一个平均分。

如果向量第一名命中恢复步骤，而两路都排在前面的通用介绍更受 RRF 青睐，融合可能反而降低首个有效证据的排名。此时可比较候选窗口、融合策略与重排，不应预设组合组件越多效果越好。

## 原理与取舍

仓库 RRF 使用 `Σ 1 / (60 + position)`，位置从一开始计数，同一路相同 chunk ID 只在首次出现时贡献分数。它利用相对位置，避免直接相加不同量纲的原始分数；代价是丢弃了原始分差信息。

手算示意：向量列表为 A、B，BM25 为 B、C，则 A 得 `1/61`，B 得 `1/62+1/61`，C 得 `1/62`。B 因两路共同支持排在前面，这只解释算法，不证明 B 的业务证据一定最好。

| 阶段预算 | 控制什么 | 过小的后果 |
|---|---|---|
| 两路候选数 | 可参与融合的证据范围 | 答案无法进入后续阶段 |
| 融合保留数 | 重排的输入规模 | 在精排前误删潜在答案 |
| 重排输出数 | 精排结果数量 | 联合证据不完整 |
| 上下文 token | 实际交给生成模型的证据量 | 条件与结论被裁散 |

## 实现示例

集成设计伪代码，非现成仓库 API，未执行：

```text
认证后生成统一的租户、权限、有效版本约束
在相同约束下获取 BM25 与向量候选
校验相同 chunk ID 对应同一版本，执行 RRF
保存不可变的融合候选与融合分数
调用重排，所有结果完成校验后再发布新排名
重排超时则使用保存的融合排名，并标记降级
去重、补齐必要邻块，按 token 预算组装上下文
```

当前重排客户端对每个 query-text 对逐条 HTTP 调用，并原地改写候选分数。若部分调用成功后发生网络或响应异常，降级排序可能混用已改写分数和原融合分数。因此“捕获异常”不等于可靠降级，应保留不可变基线并设计整体提交。

## 常见坑

不能把 RRF 分数当概率，也不能直接套用重排客户端的 `0.45` 阈值。更换重排模型后需重新标定阈值，并验证全部候选被过滤时的处理。

两路身份必须一致，否则同一证据无法正确融合，甚至混合版本。当前问答中的 `tenantId` 未传入过滤链，不能用于多租户生产知识库。离线消融仅用冻结的合成 fixture，既不调用真实索引，也不证明 RRF 优于单路或重排能提高线上成绩。

## 验证清单

- [ ] 固定语料与查询标签，对比两路、RRF、接入后的重排四组结果。
- [ ] 分别检查候选覆盖和最终排序，不把生成质量混为检索指标。
- [ ] 注入重排中途失败，确认回退排名未混合分数量纲。
- [ ] 记录调用次数、超时与上下文成本，而非只报告平均质量。
- [ ] 权限约束在两路一致执行；本文未执行基准或重排联调。
