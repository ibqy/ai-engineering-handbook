# 知识库有答案为什么检索不到

## 直接回答

“文件里有答案”不等于“查询能取回证据”。答案可能在解析时丢失、分块时拆散、导入时漏写，也可能已经进入候选却在排序或上下文裁剪时被丢弃。先找出证据在哪一层消失，不要直接换大模型或提高所有 topK。

本手册引用的是教学仓库。`/api/docs/upload` 只完成解析、分块并返回统计，没有写入可搜索索引；上传成功后立即问答失败，首先应检查入库链路，而不是归咎于 embedding。

## 实际场景

员工问“试用期出差能报销住宿吗”，制度原文写着“新入职人员经审批可按住宿标准申请”。人工打开文件能找到，但系统回答不知道。应建立一条定位记录：文件版本、证据页码、原文范围、解析文本、chunk ID、两路候选排名、最终上下文。排障日志应脱敏，只记录必要片段与标识。

如果关键词“试用期”不在原文，关键词检索可能缺少有效匹配；如果“经审批”被切到另一块，即使找到了住宿标准，证据也不完整。两者需要不同修复，不能用同一个阈值解决。

## 原理与取舍

| 观察结果 | 优先检查 | 不宜先做 |
|---|---|---|
| 解析文本中没有答案 | 扫描页、表格、清洗规则 | 扩大候选数 |
| chunk 有答案，索引无记录 | 导入目标、写入失败、版本 | 修改提示词 |
| 索引有记录，两路均未召回 | 查询表达、分词、模型和维度 | 增加生成温度 |
| 单路命中，融合后消失 | 候选窗口、ID、最终截断 | 重做全部解析 |
| 上下文有完整答案仍答错 | 条件表达、指令、证据冲突 | 无限制扩大上下文 |

检索评测应把“证据是否出现”与“答案是否正确”分开。跨段问题还应检查必需证据是否齐全，而不是命中任意一块就算解决。扩大候选有助于诊断，但会增加后续处理成本，不能替代相关性标注。

## 实现示例

排障伪代码，描述建议流程，非仓库 API，未执行：

```text
输入：问题、已标注的原文证据位置、文档版本
检查解析文本是否覆盖证据；否则停止并修复解析
映射证据到当前 chunk 集；检查条件与结论是否完整
分别按 chunk ID 读取向量侧和文本侧记录
保存两路候选、融合结果、送入模型的证据 ID
定位第一处证据缺失，只调整该层后重新比较
```

核对索引时尤其要读源码：当前 `Bm25Retriever` 默认索引是 `rag_chunks`，不能仅按 README 配置表中的 `rag_docs` 推断请求目标。`HybridSearchService` 的默认参数绑定在 `rag.hybrid.*`，而问答控制器调用显式参数重载；只改另一组配置可能影响不到该请求。

## 常见坑

离线 RRF 消融使用合成 fixture，不调用真实 embedding 或索引，不能用它证明业务问题能召回。问答请求虽然包含 `tenantId`，控制器未用它过滤；向量检索存在过滤重载也不代表调用链已启用隔离。排查时不得通过取消权限过滤来“提高召回”，更不能把跨租户内容送给模型。

Rerank 客户端尚未接入问答链，修改其阈值不会自动改善当前问答结果。上述问题必须以真实调用路径为准。

## 验证清单

- [ ] 同一问题保留原文证据、解析文本与当前 chunk 映射。
- [ ] 两路索引实际目标、ID、内容版本分别核对，而非只测端口。
- [ ] 对关键词、语义改写、跨段条件分别保存候选与失败阶段。
- [ ] 最终上下文含完整证据，并记录未命中时的拒答行为。
- [ ] 跨租户负例单独验证；本文没有执行服务联调或效果测试。
