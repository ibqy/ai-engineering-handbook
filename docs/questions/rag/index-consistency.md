# 更新删除后为什么还返回旧知识

## 直接回答

源文件、解析结果、向量索引、文本索引、缓存和会话上下文是不同副本。更新一个副本，不会自动让其他副本同步。排查应携带文档版本和 chunk ID，定位旧内容来自哪一层，再决定是补写、切换版本、清理缓存还是重建上下文。

仓库的增量更新和存储管理仍是教学骨架，新增写入、分区和删除等操作主要记录日志。`updated` 响应不是双索引一致性证明，更不是可直接部署的生产方案。

## 实际场景

制度把补贴从旧标准改为新标准，问答却时新时旧。可能向量侧仍是旧版本、BM25 已是新版本，也可能两路正确而客户端复用了旧回答。若删除后搜索不到，但后续对话继续引用旧金额，还应检查历史摘要和已构建上下文，而不是反复重建索引。

安全删除需要定义语义：是停止新查询可见，还是连在途生成也必须拦截。若要求严格撤销，应设计生成前或发送前复核；仅后台物理清理无法覆盖已取出的证据。

## 原理与取舍

建议使用稳定文档身份、处理版本、chunk 身份和有效版本指针。新版本先准备并验证，再切换可见性，最后清理旧版本；读路径必须在两路执行相同有效版本与删除约束，否则版本指针只是摆设。

| 方案 | 好处 | 必须承担的代价 |
|---|---|---|
| 先删旧再写新 | 流程直观 | 写失败会造成证据空窗 |
| 并存版本再切换 | 可验证、便于回退 | 额外空间及读路径过滤 |
| 删除标记优先 | 先阻断新查询 | 两路和缓存都要执行标记 |

指纹只能帮助识别内容变化。文件没变但解析器、分块或 embedding 版本变化，也可能需要重建。历史指纹必须从持久化状态读取；哈希一致也不能证明索引完整无损。

## 实现示例

版本发布伪代码，属于建议设计，未执行且仓库尚未实现：

```text
读取 docId 的历史有效版本与版本序号
冻结新内容、处理版本和 chunk 清单
幂等写入新版本的向量侧与文本侧
逐项核对 ID、内容哈希、数量及可查询状态
条件更新有效版本：只接受预期旧序号
通知依赖缓存失效；旧版本清理失败进入重试
删除时先登记删除状态，再阻断两路读取并清理
```

源码还揭示一个具体断点：`DocController.update` 把新 MD5 写入本次构造的 metadata，再将同一个新 MD5 传给 `IncrementalUpdater`；后者把 metadata 中的值当作历史值比较，导致该路径判断“未变更”。即使进入更新分支，所谓写入也只是日志，且删除循环遍历的是新 chunks，不能代表已查到旧版本清单。

## 常见坑

排障顺序建议固定为：确认响应对应的文档版本；绕开回答缓存查看证据 ID；分别读取两路索引；检查有效版本与删除过滤；最后检查摘要、历史消息和在途请求。不要从一句“清理完成”倒推底层删除成功。

异步任务还需防止重复执行和旧事件晚到。建议将文档版本、处理版本纳入幂等键，以单调序号拒绝旧版本覆盖。问答 `tenantId` 当前未过滤，权限撤销与删除验收也不能依赖现成隔离能力。

## 验证清单

- [ ] 模拟向量写成功、文本写失败，新版本不被提前宣告完整可见。
- [ ] 重复任务不新增重复块，旧事件不能覆盖新版本。
- [ ] 清理失败时读路径仍只见有效版本，且能对账修复。
- [ ] 删除后分别查两路，并检查缓存、历史摘要及在途生成。
- [ ] 所有完成状态有存储读回证据；本文未执行故障注入或集成测试。
