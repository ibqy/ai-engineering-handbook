# 分块大小与重叠该怎么定

## 直接回答

没有适用于所有知识库的固定块长。先定义回答问题需要的最小完整证据，再用结构边界组织文本，最后用预算限制过长块。重叠用于补偿边界损失，不是越大越安全。字符数、模型 token 数和段落数必须分别记录，不能混用。

仓库文档中的 `chunkSize=512`、`chunkOverlap=128` 是配置类初始值的说明，不是推荐效果结论，也不是所有策略的硬上限。应用实际配置和生成正文都需要核对。

## 实际场景

报销制度包含“适用人员”“城市标准”“例外审批”三段。按长度机械切割，可能把金额和适用城市拆开；整章作为一块，又会把大量无关条款送入上下文。建议先保留标题路径，让金额所在表格携带表头，让例外条件能够关联到一般规则。

对于十页长表格，“保护表格不切分”也可能超过模型输入预算。此时应设计按行组拆分并重复表头的规则，保存原始页码与行范围，而不是假定一个完整表格一定能装进模型。

## 原理与取舍

| 文档与问题特征 | 建议先比较的方案 | 重点观察 |
|---|---|---|
| 独立 FAQ，一问一答 | 按问答对分块 | 条件是否与答案同块 |
| 标题清晰的制度 | 标题、段落优先 | 同名标题误合并 |
| 连续叙述且边界不清 | 固定块长加少量重叠 | 指代、因果是否断裂 |
| 表格或代码很多 | 结构保护加超长兜底 | 表头、签名和说明是否保留 |

这些是候选设计，不代表仓库全部实现。大块可能保留语义完整性，却降低证据密度；小块更易精确定位，却需要邻块补全。重叠会增加存储和重复候选，最终 K 可能被同一段证据占满。比较时同时看证据覆盖、重复比例、块长分布和最终上下文开销。

## 实现示例

以下为分块实验伪代码，未执行，参数仅用于设计对照：

```text
冻结同一份解析结果与带原文位置的查询标签
实验一：目标 400 字符，重叠 0 / 60 字符
实验二：保持重叠 60，比较目标 400 / 800 字符
每组保存完整 chunk 快照与处理版本
重新映射“原文证据位置 → chunk ID”
用相同模型、索引条件、候选预算比较完整证据覆盖
人工复查断句、跨段条件、重复上下文和超长块
```

源码中 `FixedSizeChunker` 按段累积，超限后保留缓冲区末尾字符；它并未对每个超长段落强制二次拆分，表格和代码会独立成块。其 chunk ID 使用随机 UUID，重新运行后不能沿用旧 ID 标签直接算命中率。

`AdaptiveOverlapChunker` 只调整 overlap 元数据，没有据此拼接或裁剪正文。验证重叠必须比较相邻块实际文本，不能检查到 `adaptive=true` 就宣布策略有效。

## 常见坑

把短块全部过滤，可能删掉关键错误码或单句例外；建议先统计被过滤内容，再决定是否合并到标题或相邻段。只用平均长度会掩盖极端长段，应检查最大值及长尾样本。

分块与 embedding 同时更换，会让收益无法归因。仓库离线排名 fixture 也不衡量真实分块效果。更重要的是，上传接口只返回解析分块统计，没有导入索引；切块实验成功不等于检索链路已接通。

## 验证清单

- [ ] 金额、适用条件、否定词及例外条款未被分离成不可理解的碎片。
- [ ] 表格保留表头与来源，超长段有明确处理策略。
- [ ] 实际正文重叠与元数据一致，重复证据没有挤占最终候选。
- [ ] 每次重分块冻结版本并重映射标签，未复用失效 chunk ID。
- [ ] 仅改变一个因素后比较；本文未执行分块或检索评测。
