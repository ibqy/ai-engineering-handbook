# 首字慢和整体慢应该分别怎么优化

## 直接回答

首字慢要查回答开始之前的排队、鉴权、检索、提示词准备、模型预填充和代理缓冲；整体慢还要查生成长度、工具往返、重复推理及收尾处理。先定义“首字”为客户端看到的第一个有效内容，而不是连接建立、心跳或“处理中”。两种指标分别记录，不能拿服务端首次发送时间替代用户实际等待时间。

生产设计建议：同时观察首字延迟、端到端延迟、失败率和回答质量。流式输出主要改变用户等待方式，不保证减少生成工作量，更不能靠跳过授权与内容检查换速度。

## 实际场景

知识助手先查资料再回答，首字迟迟不来可能是检索串行调用过多；开始很快却长时间不结束，可能是输出过长或工具循环。两个问题需要不同实验：前者拆分前置阶段，后者统计输出量和每轮调用，不能只把模型换成更小的版本。

已读的 ai-platform 网关同步路径会完成模型调用后返回内容；流式路径实际拼出字符串并逐字符回调，是教学模拟，不是供应商 Token 流。用它观察到的打字效果，不能证明真实模型的首字性能或流式安全能力。

## 原理与取舍

端到端耗时取决于关键路径。无依赖的检索可考虑有界并行，但多路调用会增加连接、配额和下游负载；并行节点耗时不能直接相加当墙钟时间。先测排队时间，再决定扩容还是降低并发，避免把排队从本服务搬到供应商。

缩短提示词应保留必要证据和约束，减少输出应保留用户需要的结论。缓存能减少重复计算，但必须先满足权限和版本隔离。连接复用、预热及关闭代理缓冲都是生产设计建议，须通过真实链路验证，而不是默认已经生效。

分位数应按模型、输入长度区间、是否命中缓存分组，并同时保留超时和取消样本。只统计成功请求，会把最慢的一批排除掉。跨机器时间戳不能直接相减作为精确耗时；客户端和服务端各自测持续时间，再用请求标识关联。

## 实现示例

Java21纯逻辑示例：仅表示单次请求内的计时状态，不包含框架回调或指标上报接口。

```java
final class RequestClock {
    private final long started = System.nanoTime();
    private Long first;

    synchronized void onVisibleContent() {
        if (first == null) first = System.nanoTime();
    }

    synchronized long[] finish() {
        long end = System.nanoTime();
        return new long[] {
            first == null ? -1 : first - started,
            end - started
        };
    }
}
```

负值表示没有有效内容，不能当作零延迟。生产接入时应在客户端另设计时点，并把正常完成、取消、错误作为不同终态；服务端每个阶段另行埋点，避免只有一个总耗时而无法定位原因。

## 常见坑

- 将节点事件流称为 Token 流。工作流节点完成不代表模型已经生成首字。
- 只增加线程数，却不限制模型并发与排队长度，最终恶化尾延迟。
- 用固定休眠制造“模型耗时”，再据此宣称优化百分比。
- 只看平均值，忽略长输入、缓存未命中和重试请求。

## 验证清单

- 固定问题集和版本，分别记录冷启动、热运行、命中与未命中，不预填性能数字。
- 经过实际反向代理检查首个有效事件何时到达，排除客户端缓冲影响。
- 给慢工具、超时及取消建立样本，确认其仍进入延迟和终态统计。
- 对比优化前后证据完整性、回答长度和质量，防止把删内容误认为纯性能收益。
