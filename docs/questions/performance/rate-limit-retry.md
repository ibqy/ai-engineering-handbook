# 429限流重试和模型降级如何配合

## 直接回答

遇到限流先判断是本地入口、租户预算还是供应商容量不足。临时容量不足才适合有界重试；权限失败、参数错误和硬预算耗尽不能靠反复请求解决。重试与降级共用总截止时间、尝试次数和费用预算，不能每换一个模型就重新获得一整套额度。

生产设计建议：若供应商返回有效等待指示，应按其契约解析并与总时限比较，再增加抖动分散请求。剩余时间不足就明确结束或排队通知用户，不为了“成功率”无限等待。

## 实际场景

多个实例同时遭遇供应商限流，若都立即重发，瞬时压力会更高。业务层、客户端库和网关各自重试，还会形成尝试次数乘积。应指定一个统一的重试责任层，其他层要么关闭自动重试，要么纳入同一预算。

ai-platform 的 GatewayRateLimiter 是定时清零的进程内计数器，不能把注释中的“滑动窗口式”当作严格实现；多副本也不共享计数。同步控制器对业务响应使用 HTTP 200，因此业务字段 rate_limited 不能直接假定等于真实 HTTP 429。

## 原理与取舍

指数退避减少持续碰撞，随机抖动降低同步重发；但等待本身占用请求寿命。调度前要同时检查等待时间、下一次调用预计上限和整体剩余预算。面向交互请求宜快速反馈，长任务可以排入有容量上限、可取消的持久队列，这些都是生产设计建议。

模型降级不是单纯选择便宜模型。候选必须满足租户授权、数据处理区域、上下文长度、工具协议和结构化输出要求。供应商级故障时切换同供应商另一个模型未必有效；降级后应记录实际模型和能力差异，不应继续宣称原等级服务。

重试生成与重试副作用应分开。工具超时可能已经完成写操作，不能仅因没收到响应就再次执行。应按幂等键查询或恢复既有操作；无法确认时转人工核对。已经向客户端输出一半答案时，也不要无提示地把另一模型续文拼上去。

## 实现示例

伪代码：以下状态机是生产设计建议，不是仓库现有接口。

```text
收到失败后：
  若身份无效、参数错误或预算耗尽，则结束
  若操作结果未知且有副作用，则查询幂等记录或转人工
  若可重试且次数、费用、整体时限仍允许：
    计算满足供应商等待要求的退避时间并加入抖动
    等待后重新检查取消信号与剩余预算
    在同一请求账本下增加一次尝试
  否则筛选符合权限、数据区域和协议要求的备选模型
  若有合格备选且仍有预算，则记录降级并调用
  否则返回可解释的终态
```

重试等待不应通过忙循环实现；取消信号也必须能终止等待。记录原始错误分类和尝试链，用户可见信息则应去掉密钥、内部地址及供应商敏感细节。

## 常见坑

- 把请求数限流与 Token 配额混为一谈，大请求仍可能耗尽容量。
- 每个降级分支独立重试，导致总次数失控。
- 使用虚拟线程就放弃背压，任由本地排队无限增长。
- 将模型路由器存在误认为已接好真实供应商切换；选中名称不等于实际执行已切换。

## 验证清单

- 注入临时限流、硬配额失败及错误等待指示，检查是否进入正确分支。
- 统计全链路实际尝试数，确认客户端库没有隐形额外重试。
- 在退避期间取消请求，检查是否停止后续尝试和预算占用。
- 让备选模型不满足权限或协议要求，确认拒绝降级而不是绕过限制。
