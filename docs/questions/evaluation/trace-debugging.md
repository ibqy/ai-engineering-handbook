# 偶发错误怎么通过执行轨迹定位

## 直接回答

为一次请求保留可关联、可解释的执行轨迹，逐层寻找“第一次偏离预期”的位置。至少关联任务、子任务、节点、模型调用和工具操作，记录状态变化、耗时、错误类别及版本。最终答案和一条异常栈往往不足以区分模型问题、检索问题与调度问题。

轨迹不是把全部提示词和模型思考永久存下来；优先记录结构化动作、证据标识与简短决策理由，并对敏感内容脱敏。

## 实际场景

用户偶尔收到不完整研报。先查两路检索是否都返回，再查融合截断是否丢掉关键证据，接着核对上下文是否因长度限制裁掉片段，最后才判断模型是否忽略已有资料。若直接重新生成，多半只能得到“这次好了”，不能解释原来的失败。

审批场景还要比较审核前后检查点、实际进入的节点与外部操作编号。收到子图结束事件，不代表根任务已经完成；流断开也不代表工具没有执行。

## 原理与取舍

AgentTraceLogger 创建工具 span，记录任务 ID、工具名及截断后的观察；异常路径设置错误状态。这提供局部证据，但该类本身没有建立完整任务父 span 或展示跨线程上下文传播，不能据此声称端到端链路天然完整。

AgentTaskService 在工具执行后记录步骤快照，记录中的子任务标识传入 null；循环防护在工具 span 创建前即可返回。因此定位预算或重复调用拦截时，不能只查工具 span。步骤快照采用加载、追加、保存路径，并发写入是否丢记录也需要另测。

LangGraph4j 运行器则保留已访问节点、检查点历史和终态，并依据根生成器的 GraphResult 判断完成或中断，而不是看见任意 END 就完成。这说明事件顺序、层级和终态语义必须一起解释。

生产建议把 traceId 与业务 operationId 分开：前者追踪一次执行，后者识别同一业务动作的重试。版本信息包含模型、提示词、图定义、语料和索引；没有这些信息，复现可能已经换了环境。

## 实现示例

以下为伪代码，表达排障步骤而非现有查询 API：

```text
# 伪代码
按任务ID收集节点、模型、工具和审批事件
按父子关系与事件序号重建路径，不仅按墙钟排序
对比成功样本，定位首次状态或证据差异
若候选缺失：检查索引、过滤与查询版本
若动作重复：检查恢复点、重试原因和幂等凭证
用记录的工具响应做只读回放，再构造最小回归用例
```

回放默认不执行付款、邮件或删除；需要复验外部行为时使用沙箱和新测试对象。捕获的响应可能包含个人数据，应按最小必要范围保存，设访问控制、留存期限和删除机制。

## 常见坑

只有文本日志而无关联 ID，无法区分并发任务；只保留成功轨迹，偶发错误恰好被采样丢弃；截断文本后把缺失信息误判为模型没见过资料，都会误导定位。

span 正常结束也不一定业务成功，工具可能把错误编码成字符串返回。反之，future 被取消不能证明底层线程或远程请求已停止，必须查操作结果与副作用凭证。

## 验证清单

- 一次失败能否串起请求、子任务、模型、工具与审批？
- 是否记录拦截、超时、重试、取消和未知结果，而不只成功？
- 并行与恢复后，父子关系、版本和事件序号是否仍正确？
- 能否在不触发真实副作用的条件下回放？
- 根因修复是否转成确定性回归测试，并经过脱敏检查？
