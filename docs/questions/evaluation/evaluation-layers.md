# AI应用要测哪些层而不只看答案

## 直接回答

至少分开测五层：确定性逻辑是否正确，外部依赖契约是否成立，证据检索是否有效，生成答案是否可信，以及整条链在失败、恢复和负载下是否可靠。最后再观察真实业务成效。答案看起来正确，只能说明一个样本的一次输出，不能证明这些层都合格。

## 实际场景

知识助手回答了正确的退款时限，却引用另一租户的文档，仍是严重失败。审批助手给出合理建议，却在拒绝后继续执行工具，也不算成功。反过来，模型暂时不可用时，系统如果正确拒绝执行并保留任务状态，可靠性层可以通过，但该请求的业务目标仍未完成。

因此报告不应只有一个“通过率”，而应说明测量对象、样本数、失败类型和依赖环境。

## 原理与取舍

第一层用确定性测试验证参数解析、路由、状态合并、公式和非法输入；第二层用契约或集成测试检查真实服务响应、超时和错误映射。Mock 可以验证调用方式，不能证明真实凭证、索引和网络可用。

第三层固定查询、语料版本与相关证据标签，测召回和排序；第四层固定生成配置，核对事实支持、完整性、引用和拒答。rag-hybrid-search-demo 的 EvalRunner 只计算检索排名指标，虽然持有检测器字段，但 evaluate 没有调用它，也不使用标准答案评分。因此其报告不能充当答案正确率或幻觉率。

第五层检验审批中断、并发恢复、取消、故障注入和预算约束。Spring AI Alibaba 的运行器测试包含重复审批、两级审核和递归耗尽失败；这些断言针对执行语义，而不是模型智能。上线后的转人工率、问题解决率等指标，还应结合流量结构和人工抽检解释。

分层不是各测各的就结束：最终需要端到端样本把层间关系串起来，保留检索证据、模型输出、工具动作及终态，以定位是哪一层首次偏离预期。

## 实现示例

以下是伪代码，表示测试组织方式，不是仓库已有测试入口：

```text
# 伪代码
逻辑回归：固定输入 → 验证路由、公式、非法状态
依赖契约：真实沙箱 → 验证超时、响应和权限拒绝
检索评测：固定标签 → 保存逐查询候选与排名
答案评测：固定证据 → 人工或校准后的裁判核验
可靠性演练：注入故障 → 核验终态、重复副作用与恢复
上线观察：分层抽样 → 联合业务结果与执行轨迹复盘
```

每条报告记录应用修订、数据版本、运行模式和实际调用的依赖。门槛应在独立验证集和业务约束上预先确定，不能先看测试结果再随意选择一个容易通过的标准。

## 常见坑

让离线模型输出固定答案，再宣称真实模型正确率稳定；只跑 Mock 测试却写“端到端通过”；把测试文件存在说成本次测试通过，都是证据范围错误。合成排名测试只能验证给定候选上的公式和融合行为，不是线上检索性能。

总平均还会掩盖少数关键失败。应单独展示高风险操作、长尾问题、多证据问题及无答案样本，不能用普通问答数量稀释越权事件。

## 验证清单

- 每项指标是否写明分母、样本划分与适用层次？
- 离线、Mock、真实依赖和线上观察是否清楚区分？
- 是否保留每条失败样本，而不只汇总均值？
- 是否测试拒绝审批、空召回、依赖超时与重复恢复？
- 更换模型、提示词、分块或框架版本后，是否重跑相关层？
