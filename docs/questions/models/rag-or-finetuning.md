# 长上下文、RAG 和微调如何选择？

## 直接回答

先判断问题缺的是“本次需要的资料”还是“稳定执行任务的能力”。少量、一次性的完整材料可以先试长上下文；经常更新、需要按权限检索和引用的知识适合 RAG；已有稳定任务定义和足够高质量样本，却仍存在持续的风格或行为偏差时，再评估微调。三者可以组合，不是互斥产品菜单。

不要因为模型答错就立即微调。先检查资料是否缺失、检索是否漏召回、提示词是否冲突、输出校验是否合理。错误发生在哪层，就优先改哪层。

## 实际场景

法务要比较两份刚上传的合同，可先把两份材料完整交给模型，同时保留条款位置。企业客服每天更新产品政策，且不同客户能查看的文档不同，更适合带权限过滤和版本管理的检索。若客服始终无法按固定格式解释复杂拒赔理由，才考虑用审核过的样本改进任务行为。

同一个客服系统也可以先检索政策，再把命中的完整章节放入较长上下文，并由经过任务适配的模型组织答案。组合方案的复杂度更高，因此必须证明每个新增环节解决了可测量的问题。

## 原理与取舍

长上下文减少了显式召回步骤，却不保证模型会利用每一处细节；无关内容、重复版本和材料位置都可能影响结果。预算不仅包含输入，还包括系统规则、历史、工具描述和输出。不能只看宣传的最大窗口就把整个资料库塞入一次请求。

RAG 把知识放在可更新、可追溯的数据层，代价是抽取、分块、索引和召回可能损失证据。评估时要分别检查“正确片段是否出现”和“模型是否正确使用片段”，否则会把检索失败误判成模型能力差。

微调调整参数，更适合学习反复出现的任务模式；不宜把经常变化的价格、库存或租户权限当成参数中的事实数据库。它还引入样本治理、训练成本、版本回滚及数据泄漏风险。先改善提示词与样例，建立独立测试集，再比较微调带来的增量收益。

## 实现示例

伪代码：用于讨论方案，不是框架路由 API；条件可能同时成立，需要组合评估。

```text
if 材料有权限限制或持续更新:
    候选方案加入“权限过滤后的检索 + 证据引用”
if 本次材料范围明确且完整输入在预算内:
    候选方案加入“完整材料上下文”
if 已定位为稳定任务行为偏差且有合格训练样本:
    候选方案加入“微调模型 + 原有证据链”
对每个候选方案:
    固定任务集，评估正确性、拒答、证据和完整成本
选择满足约束且维护成本可接受的最简单方案
```

对照实验还应包括“检索命中正确但含旧版本”“关键依据位于长文中间”“问题根本无依据”三类反例。这样才能知道改善来自信息供给还是输出习惯变化。

## 常见坑

- 用微调记忆最新政策，却没有更新、撤回与引用机制。
- RAG 只测最终回答，不保存命中文档及版本，无法定位漏召回。
- 长上下文塞入全部租户材料，再要求模型自行保密。
- 微调与验收集包含同一合同的不同切片，造成效果虚高。

## 验证清单

- [ ] 先将错误归类为资料、检索、推理或输出问题。
- [ ] 测试集按原始文档或业务实体隔离，避免样本泄漏。
- [ ] 过期资料可失效，引用能返回正确版本的原文。
- [ ] 所有方案都包含无依据拒答、权限边界和更新后的回归测试。
