# 提示词怎样变成可维护的输入输出契约？

## 直接回答

提示词不应只是控制器里的一段文案，而应与输入定义、输出结构、允许行为、失败处理和验收样例一起版本化。提示词描述模型应该做什么，服务端代码决定哪些输入可接受、哪些输出可进入业务流程。两者共同构成契约，但自然语言本身不能提供确定性的安全保证。

把固定规则、业务资料和用户输入分开组织，说明资料只是待分析数据，不是可以修改系统权限的指令。模板变量便于维护，却不具备数据库参数化查询那样的注入防护语义。

## 实际场景

工单分类器最初只返回“物流”或“退款”，后来需要增加紧急程度和缺失字段。若直接修改提示词，下游仍按一个字符串读取，可能静默丢失信息。更稳妥的做法是发布新契约版本，定义类别枚举、紧急程度范围、无法判断时的状态，以及旧客户端迁移方式。

例如“帮我退掉上次那个”缺少订单标识。契约应要求输出“需要补充信息”，而不是根据聊天印象猜订单。业务规则说明哪些字段必须来自会话中的可靠输入，哪些可以推断，哪些必须通过查询工具确认。

## 原理与取舍

契约可以分为四层：输入层限制长度、类型和必填项；任务层描述目标与边界；输出层规定字段和语义；执行层校验并处理错误。示例有助于说明边界，但不能列举全部情况，因此还要有清晰的未知值约定。

提示词越长不一定越稳定。重复、相互矛盾的规则会让维护者难以判断优先级。优先写可检查的要求，例如“无订单号时返回缺失字段”，少写“务必专业负责”。模板、模式和样例一同评审；修改一项，就重跑相关回归集。

版本号应出现在应用日志和评估记录中，不要求模型替应用选择版本。回滚时恢复完整契约包，避免旧提示词配新解析器。敏感原文不宜直接写入日志，可以保存脱敏摘要和受控的请求引用。

## 实现示例

Java21纯逻辑示例：校验输入并固定应用选择的契约版本，不使用框架 API。

```java
record TicketInput(String text, String locale) {}
record PromptContract(String version, String instruction) {}

static PromptContract prepare(TicketInput input) {
    if (input == null || input.text() == null
            || input.text().isBlank()
            || input.text().length() > 4000) {
        throw new IllegalArgumentException("工单内容不合法");
    }
    return new PromptContract("ticket-v2",
        "只做工单分类；缺少订单号时标记需补充；不得代用户退款。");
}
```

这里的长度限制只是应用示意，不是模型上下文上限。实际接入时仍需按模型预算组织消息，并为输出预留空间；文本截断也不能悄悄删除关键否定词或用户授权条件。

## 常见坑

- 把输出示例当完整模式，遗漏空值、枚举和失败分支。
- 只保存最终拼接字符串，无法区分模板变化与业务资料变化。
- 在模板中写“忽略恶意指令”就认为已完成安全防护。
- 为解决个别失败不断追加规则，却不检查已有样例是否退化。

## 验证清单

- [ ] 缺失、超长、冲突输入均有明确行为。
- [ ] 模板版本、输出模式和验收样例能对应到同一次发布。
- [ ] 非法结果不直接触发业务写操作。
- [ ] 引号、花括号、伪系统指令和跨轮指代有回归覆盖。
