# 如何选模型而不是只看榜单？

## 直接回答

榜单用于缩小候选范围，不用于替代验收。先确认数据能否出域、是否支持所需输入模态、上下文是否够用、部署地区和调用配额是否符合要求；这些是门槛，不应被综合评分抵消。再让候选模型完成同一批业务任务，比较可验收结果、失败方式、端到端延迟和每个成功任务的成本。

“最强模型”不一定是整个系统的唯一模型。简单分类可以独立路由，复杂分析走另一条路径，但每条路径都要有验证过的适用范围。升级模型也不能绕过隐私约束或用户授权。

## 实际场景

电商客服包含政策问答、订单查询和退款申请。政策回答需要证据，订单查询需要正确选择工具，退款申请还需要明确授权。只用闲聊题测模型，会漏掉订单号提取错误、工具参数缺失和未经确认直接申请退款等关键问题。

准备脱敏历史问题，覆盖口语、错别字、信息不足、跨轮指代和恶意指令。标签不只写“答案是否好”，还应标注应调用的工具、必须追问的字段、允许引用的证据以及禁止发生的动作。训练提示词的样本与最终验收样本分开保存。

## 原理与取舍

模型能力与应用效果之间隔着提示词、检索、工具、网络和后处理。公平比较时先固定这些条件，再单独试验模型专用优化；否则无法解释收益来自哪里。记录模型标识、调用日期、采样参数和上下文版本，托管服务的同名模型也可能随时间变化。

成本应计入输入、输出、重试、工具请求和人工接管。只比较每百万 token 单价可能选中“便宜但经常重做”的方案。延迟同时记录首次可用内容和最终业务完成时间，流式首字快不等于退款确认快。报告成功与失败样本的分布，不只给成功请求平均值。

## 实现示例

Java21纯逻辑示例：硬约束过滤后按预算筛选，阈值由业务验收决定，不代表推荐数值。

```java
record Candidate(String name, boolean compliant,
                 boolean capable, double passRate,
                 long p95Millis, double costPerSuccess) {}

static boolean acceptable(Candidate c, double minPassRate,
                          long maxP95Millis, double maxCost) {
    return c.compliant() && c.capable()
        && c.passRate() >= minPassRate
        && c.p95Millis() <= maxP95Millis
        && c.costPerSuccess() <= maxCost;
}
```

先检查测量数据完整、指标有限且单位一致；没有成功任务时，单次成功成本应标记不可计算，不能填零。通过门槛后保留质量、延迟、成本的对照表，由业务确认取舍，而不是把安全性折算成便宜几分钱。

## 常见坑

- 用框架支持某能力推断当前供应商、模型和端点也支持；必须测试实际组合。
- 把缺失用量当成免费，把未配置单价的零成本当成真实账单。
- 降级时自动移交另一个地区或供应商，意外改变数据处理边界。
- 只测一次且只看均值，忽略波动、限流和长请求失败。

## 验证清单

- [ ] 硬约束有书面判定，所有候选使用同一验收集。
- [ ] 关键业务错误单独统计，不能被普通问答的高分稀释。
- [ ] 记录超时、重试、工具调用和人工接管成本。
- [ ] 小流量上线后可按模型版本回滚，并持续抽样复核。
