# 持续补充与纠错

原则：**一个问题、一篇 Markdown、一个稳定编号。** 在已有分类中增加文章，不必修改首页、搜索配置或侧边栏清单；重新构建会自动收录。

## 最简单的三种方式

1. **只想记录问题**：到 [GitHub Issues](https://github.com/ibqy/ai-engineering-handbook/issues/new/choose)选择「补充一道问题」，写场景、现象和希望解决什么；不要附密钥或公司原始数据。
2. **修正一篇文章**：在文章底部点击「在 GitHub 补充或纠错」，编辑后提交变更。非维护者通过 Pull Request 合入。
3. **新增完整问答**：在仓库对应分类目录创建 Markdown，填写元数据和七个章节，运行校验后提交 Pull Request。

Issue 是选题收集箱，不会自动变成答案。内容仍需核对、编辑和验证，避免把未经证实的建议自动发布。

## 分类与编号

| 目录 | 分类 | 编号前缀 |
| --- | --- | --- |
| `models` | 模型与提示词 | M |
| `rag` | RAG 与知识检索 | R |
| `tools` | 工具调用与 MCP | T |
| `agents` | Agent 与工作流 | A |
| `memory` | 记忆与上下文 | C |
| `multimodal` | 多模态 | V |
| `evaluation` | 评测与排障 | E |
| `performance` | 性能与成本 | P |
| `security` | 安全与权限 | S |
| `production` | 生产部署 | D |

文件位于 `docs/questions/<目录>/<英文短横线名称>.md`。先搜索现有编号，选择分类中下一个未使用编号，不重排旧编号；例如模型类已有 M01–M04，则新增 M05。`order` 决定类内顺序。

新增分类时，才需要修改 `docs/.vitepress/categories.mjs`，同时更新本表和仓库 README 的分类入口。

## 元数据示例

下面只是格式示例，新增文章时填写真实内容和日期，不要把说明文字当作完成的文章提交。

```yaml
---
id: M05
title: 如何判断模型升级是否值得？
category: models
level: 高阶
tags: [模型升级, 回归评测]
summary: 在冻结业务集上比较收益、成本与回归，再按流量灰度。
updated: '2026-11-11'
order: 5
---
```

`level` 仅允许「基础」或「高阶」。日期加引号，表示本篇实际复核日期，不要每次构建自动刷新。标题最好是读者真的会问的问题；摘要必须能给出判断，而不是「本文介绍了……」。

## 必备内容

正文使用一个一级标题，并按以下二级标题组织：

1. **直接回答**：先给结论和关键适用条件。
2. **实际场景**：描述输入、约束和失败表现，虚构业务例子要明确是示例。
3. **原理与取舍**：比较候选方案，说明不适用范围。
4. **实现示例**：标明伪代码、Java 纯逻辑或仓库摘录，写清依赖和省略边界。
5. **常见坑**：给出反例，而不是泛泛写「注意安全」。
6. **验证清单**：包含失败路径、判定依据和需要真实服务验证的部分。
7. **关联项目与参考**：链接实际核对过的源码或官方材料，标明教学简化；别链接猜出来的类名。

正文引用本手册其他问题时，推荐使用相对 `.md` 链接，GitHub 和阅读站都可以打开。不要把 `{{ }}` 形式的模板直接写成普通正文；放入代码块，避免被当成 Vue 模板编译。

## 本地检查

要求 Node.js 22 或更新的受支持版本。

```bash
npm ci
npm test
npm run build
npm run dev
```

- `npm test` 验证目录读取、元数据约束和筛选逻辑。
- `npm run build` 先校验分类、稳定编号、字段、章节与引用，再由 VitePress 检查站内链接并生成静态站点。
- 新增文章后重启开发服务，确保服务启动时生成的侧边栏也重新收录。正式构建始终重新扫描所有文章。
- 内容校验不是事实核查，更不证明文中的 Java 片段和外部服务已运行；需要作者逐项确认。

浏览器回归测试：

```bash
npx playwright install chromium
npm run test:browser
```

若本地同级目录还克隆了被引用的教学仓库，可额外执行 `node scripts/check-content.mjs --local-sources` 检查引用路径；CI 不要求克隆其他仓库。

## 自动发布的边界

Pull Request 只做校验、构建和浏览器测试；合并到 `main` 后才部署 GitHub Pages。失败的构建不会替换线上站点。首次发布需要维护者创建 GitHub 仓库并在 Pages 中选择 GitHub Actions。

Pages 只提供静态阅读，不运行 Java 后端，不提供在线模型聊天，也不存储密钥。
